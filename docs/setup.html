First-time setup · one checkpoint at a time

Connect your domain, carefully.

Follow the steps in order. Check a step only after its stated check passes. If it fails, fix that step before moving on.

This is Cloudflare forwarding to any inbox you own (Gmail, Outlook, iCloud, Proton, …), plus an optional manual Gmail send-as step for sending, not a new mailbox or Google Workspace setup. If you only need to receive mail, skip step 13. These checkmarks are your record, not automatic verification. The page makes no provider requests and accepts no credentials.

The short version: a few simple steps. Use the reviewed development source snapshot (not v0.1.0) until a compatible release/installer ships. Check prerequisites (step 1), review/select source (step 2), run ./cmail setup, then send yourself a test (step 14). ./cmail setup carries out steps 3–12 for you and pauses only for browser approvals, the Cloudflare token, the nameserver confirmation and one verification click; read those steps to review or troubleshoot. Sending is optional and only on request in this source workflow: step 13 (./cmail send-as) is not part of the default setup.
Gmail outbound policy warning (optional sending only). Google announces third-party “Send as” removal starting January 2027. Confirm current availability before committing to this optional sending path. Inbound forwarding is separate and needs no Google account. If Gmail or account policy blocks aliases/App Passwords, stop the outbound steps and choose an approved mail provider outside this guide; do not bypass security controls.

Progress belongs to this browser profile and site origin; it does not sync. Reset only clears this checklist, not your accounts. Avoid shared profiles. Multiple tabs use the last saved change.

  1. Gather the prerequisites and decide the scope

    1. Use macOS or Linux, a trusted local terminal, Bash 3.2+, curl and standard utilities. Git is needed only for the clone route below. Python 3 is optional for the safe config checker.
    2. Have a GoDaddy account controlling the domain, a Cloudflare account, access to your receiving inbox (any provider; a Gmail/Google account only if you also want to send), and a different independent mailbox for tests. Registrar support here is GoDaddy only.
    3. Choose DOMAIN (bare domain, no URL/path), DEST_EMAIL (full receiving address, any provider), and ADDRESSES (comma-separated local parts such as hello,contact, not full addresses). Decide whether any aliases need sending; receiving alone needs no Gmail setup.
    4. Inventory existing website, mail/MX, TXT/SPF, subdomain and other DNS records; identify DNSSEC/DS records and any existing mail provider. Plan the migration and downtime before changing delegation or mail records.
    5. Only if you want to send: check the Gmail policy warning above and whether your Google account permits App Passwords. For business-critical sending, assess an approved mail service instead.

    Check: You own/control the intended domain, can open both provider accounts and your receiving inbox, and have a DNS/mail migration plan. Missing access is not a reason to buy another domain.

  2. Select reviewed current source (or legacy installation)

    For this guide’s receive-only/optional-send workflow, clone upstream and select the immutable feature revision below. This is a reviewed development source snapshot, not v0.1.0, until a compatible release/installer ships. Fetch the pin explicitly; it need not be advertised on the default branch. Review cmail and lib/ before execution:

    git clone https://github.com/luongnv89/cmail
cd cmail
git fetch origin cda65f0554a870ed8079e93741a331918118acec
git checkout --detach cda65f0554a870ed8079e93741a331918118acec
./cmail help

    Keep this checkout for the checker/skill. Use ./cmail, never PATH cmail, in the following steps; config defaults to checkout .env.

    Legacy installation alternative (not this quickstart): after reviewing install.sh and the distribution contract, bash install.sh downloads the pinned v0.1.0 runtime regardless of checkout revision. Its setup still includes the Gmail guide and it lacks send-as. v0.1.0 itself contains neither this installer nor the newer skill/checker. No released remote bootstrap or Homebrew package is promised.

    Legacy default launcher: ~/.local/bin/cmail; runtimes: ~/.local/share/cmail/runtime.*; config: ~/.config/cmail/.env. Installation needs Bash/curl/standard utilities, no sudo, git, jq, gddy or provider credentials (git only for cloning); it neither starts setup nor edits shell profiles. Use user-controlled, non-symlink destinations and parents. Overrides CMAIL_BIN_DIR, CMAIL_DATA_DIR, CMAIL_CONFIG_DIR must be absolute directories. Existing config is preserved. Verify the trusted installed launcher with "$HOME/.local/bin/cmail" help. To reuse its config with source, export ENV_FILE="$HOME/.config/cmail/.env" for every source command and check that same file in step 7. Do not edit a retained runtime’s config.

    Check before setup: Trusted ./cmail help loads offline and lists setup/send-as/status/doctor/help. If send-as is missing, stop: this is not the runtime for this source workflow. Help is not proof of provider access or delivery.

  3. Prepare runtime dependencies before setup

    Check your trusted tools locally:

    bash --version
curl --version
jq --version
gddy --version
gddy --help

    Missing curl/jq: install with your existing OS package manager after reviewing the change. Missing gddy: follow GoDaddy’s CLI installation guide; review its installer before running it. Its default ~/.local/bin needs to be on PATH. Compare gddy tree / help with the domain and nameserver commands cmail uses.

    ./cmail setup and ./cmail doctor may install missing tools (sudo/package manager or the latest gddy installer). Doctor/status may create or secure local config; doctor can print non-secret config. They are not the optional checker below and not offline help. Current gddy purchase syntax can differ from cmail’s pinned workflow: if command compatibility is uncertain, use staged dashboard actions rather than blindly running setup.

    Check: Bash/curl/jq/gddy work from trusted paths and the installed gddy supports the needed commands. If not, stop and resolve compatibility; no provider writes are needed for this check.

  4. Authenticate to GoDaddy and verify an owned domain

    1. Prefer local browser OAuth: run gddy auth login --env prod, sign in to the intended GoDaddy account, and review consent. Inspect gddy auth status --json privately for an unexpired prod session.
    2. In GoDaddy’s domain portfolio, open the exact domain and its DNS → Nameservers. Locally inspect gddy domain get 'example.com' --env prod --json, replacing example.com with your owned domain. Check ownership and readable current nameservers; do not post raw output.
    3. Set GDDY_ENV=prod for real resources. ote is a sandbox; it cannot prove production ownership or live delivery.

    Optional headless PAT (not required for OAuth)

    Sign in to Personal Access Tokens → + Generate Token. Choose a descriptive name and expiration, expand Domains & DNS, and grant domains.domain:read for reads and domains.nameserver:update only if approving nameserver replacement. domains.domain:create is needed only for a separately approved registration; do not select every capability by default. Generate, copy the one-time secret to a password manager and save GDDY_PAT in private local config. Never enter it here, in chat, or in a recorded command.

    Current GoDaddy documentation specifies Authorization: Bearer <PAT> for Domains v3 at https://api.godaddy.com. Legacy v1/v2 classic keys use Authorization: sso-key <key>:<secret>; cmail has no key/secret fields and does not need them for its gddy OAuth/PAT route. Environment selection is delegated to gddy --env, not a header you supply in cmail. In the inspected upstream CLI, built-in prod uses https://api.godaddy.com and ote uses https://api.ote-godaddy.com; local configuration can override endpoints. Its Domains client sets Authorization and x-request-id headers, not an environment-selector header. Do not assume an OTE header or credential turns a production request into a sandbox. Verify your installed CLI’s environment and endpoint behavior before using OTE; this source observation is not proof for every installed version. Newly issued PATs, OAuth status and newer API docs do not by themselves establish pinned-runtime compatibility.

    If you do not yet own a domain

    Stop to choose and register it deliberately in the GoDaddy dashboard, reviewing domain, price, term, renewal, contacts and payment method. Then repeat the exact-domain read. cmail can offer registration when DOMAIN is blank and an entered domain is not confirmed owned; it asks to attempt registration and confirm the quote before purchase. Setting an existing DOMAIN skips that picker, so fill it only after verifying ownership. A network/access error is not evidence that a purchase is needed. After any purchase timeout, inspect orders, billing and ownership before retrying; current gddy purchase arguments may differ from the pinned script.

    Check: An exact-domain read succeeds in the intended production account with current nameservers. PAT presence or an auth message alone is insufficient.

  5. Select the Cloudflare account, zone and IDs

    1. Sign in to Cloudflare and select the intended account. Look for the domain under Domains (older layouts: Websites). Reuse an existing zone; do not create a duplicate because a token cannot see it.
    2. If genuinely absent, explicitly approve adding the domain (a provider write), use the dashboard’s add/onboard-domain action, choose the appropriate plan, review imported DNS and finish onboarding. Do not change GoDaddy nameservers yet. cmail setup can also create a missing zone, but is not a staged read-only check.
    3. Open that domain’s Overview → API section and copy Zone ID and Account ID separately. Account ID can also be copied through dashboard Search → “Copy account ID”. Both are normally 32 hexadecimal characters, but they identify different resources.
    4. Record the assigned Cloudflare nameserver set privately and compare domain/account identities. These are assigned to your zone; never use example nameservers.

    CF_ACCOUNT_ID selects the account for zone creation and bypasses account discovery only; it grants no permissions. Set it if discovery sees zero/multiple accounts. CF_ZONE_ID identifies this domain’s zone and is saved by setup; status uses it. On an existing zone, account-level destination operations use the account owning that zone, not an unrelated configured account.

    Check: You know which account owns which exact zone and have its IDs/assigned nameservers. Dashboard visibility is not proof that a token has access.

  6. Create the scoped Cloudflare user API token

    1. Open My Profile → API Tokens → Create Token → Custom token / Get started. Use a user API token for cmail’s /user/tokens/verify flow, not the Global API Key.
    2. Add these five permissions for the current cmail workflow:
    Cloudflare permissions required by cmail
    ScopePermissionAccess / purpose
    ZoneZoneEdit — zone lookup/creation
    ZoneZone SettingsEdit — routing DNS activation
    ZoneDNSEdit — DNS configuration
    ZoneEmail Routing RulesEdit — forwarding rules
    AccountEmail Routing AddressesEdit — destinations in owning account
    1. Under Zone Resources, Include the specific existing domain; for creating a zone, include the intended account’s zones. Under Account Resources, Include the same owning account. Do not grant all accounts as an automatic workaround.
    2. Review expiration/optional client-IP restrictions, Continue to summary, review, Create Token. Copy the secret once to secure local storage; paste it into CLOUDFLARE_API_TOKEN only in your private editor or the CLI’s hidden prompt. Never paste it into this page or share screenshots of the token.

    Check: The five permissions and correct resource scopes are granted. “Active” from token verification means activity only, not access to your domain/account or successful writes.

  7. Fill and check private literal configuration

    For the source workflow use checkout .env (default for ./cmail). Preserve any existing file. For a new file only, from the reviewed checkout, after verifying user-owned non-symlink parents:

    (umask 077; cp -n .env.example .env)
chmod 600 .env

    Alternatively reuse installed default ~/.config/cmail/.env (or install-time CMAIL_CONFIG_DIR) via an explicit runtime ENV_FILE. Export that selected path before every ./cmail command, and use the same path for both checks below.

    Edit locally, without recording or sharing the editor. Use documented KEY='literal value' assignments, no spaces around =, no duplicates or unknown keys. Config is trusted Bash and runtime evaluates it twice: no commands, $(), backticks, expansions, scripts or multiline values. Do not source it as a validation step.

    • Required filled values: DOMAIN, DEST_EMAIL, ADDRESSES, CLOUDFLARE_API_TOKEN.
    • Set GDDY_ENV=prod. GDDY_PAT is optional for OAuth; CF_ACCOUNT_ID and CF_ZONE_ID must match your resources when set. DRY_RUN is optional 0/1 and affects nameserver preview only.
    • No Google password belongs in .env. App Passwords go directly into Gmail’s dialog.

    The newer checkout contains an optional read-only checker; it is not installed by install.sh. From that checkout, run (use your actual file path if different):

    python3 skills/cmail-setup/scripts/check_config.py .env
bash -n .env >/dev/null 2>&1

    The checker never sources or prints values. It requires a regular user-owned non-symlink file with mode 600, known keys and conservative LF-only literal syntax. If Python is unavailable, manually review ownership, permissions, all fields and literal-only content locally; do not call an unrun checker green. In a source checkout confirm git check-ignore .env succeeds and git ls-files --error-unmatch .env fails. Never commit config; rotate leaked credentials.

    Check: Both local checks pass and values match your intent. This checks config, not live credentials or provider access. See the checker’s exact contract.

  8. Verify actual token access before any migration

    Use the actual configured token in a trusted, unrecorded local API client. Follow the setup skill’s access gate: read-only GETs to /user/tokens/verify, /zones/<zone-id> and /accounts/<owning-account-id>/email/routing/addresses on https://api.cloudflare.com/client/v4. Enter token through protected local input/storage, never chat, captured tools or shell history. Do not publish request headers or full responses.

    Check: Each read returns HTTP 2xx and API success; token is active; exact-zone response matches DOMAIN and owning Account ID with assigned nameservers; owning-account destinations are readable. Read success does not prove write permissions: review token grants and check each operation’s resulting state later.

    On 401/403, fix the operation’s permission/resource scope. Zero visible accounts: confirm Account Resources and optional correct CF_ACCOUNT_ID. Multiple accounts: select one explicitly. An empty zone list is not proof of absence; inspect dashboard inventory before creation. An active token alone is never enough.

  9. Migrate DNS, then replace nameservers deliberately

    1. Copy/review existing web, mail, TXT and other service records in Cloudflare DNS. An automatic import may be incomplete. Plan DNSSEC/DS transition with registrar/provider guidance so old DS records do not invalidate new delegation.
    2. Compare GoDaddy → exact domain → DNS → Nameservers with Cloudflare Overview’s complete assigned set. If already matching, skip the write.
    3. Only after approval of the exact domain, complete replacement set and migration plan, change nameservers through the registrar dashboard (or a reviewed compatible CLI). This replaces all nameservers and can interrupt websites/mail.
    4. Read fresh registrar state and wait for Cloudflare to show Active. A submitted update is not activation. cmail polls for about 20 minutes; propagation may take 24–48 hours. Wait and recheck rather than repeatedly writing.
    Do not use setup as a safe preview. DRY_RUN=1 ./cmail setup previews only GoDaddy nameserver replacement. It can still create Cloudflare zones, enable routing/DNS, register destinations, create rules or offer paid registration. The monolithic command does not enforce this guide’s external gates. Prefer staged dashboard actions or the separate cmail-setup skill. If you choose the CLI, review every pending operation first and stop at any mismatch.

    Check: A fresh registrar read shows the exact assigned set and Cloudflare shows this domain Active. If available, corroborate with a public DNS NS lookup. After uncertain writes, inspect both dashboards before retrying; cmail does not roll back delegation.

  10. Enable Cloudflare Email Routing after mail review

    1. In the current dashboard go to Compute → Email Service → Email Routing, select/onboard the domain. Older layouts put Email → Email Routing under the domain. Follow Cloudflare’s current routing guide if labels differ.
    2. Review proposed routing MX/TXT (SPF and any DKIM) records against your existing mail service. Do not delete old MX/TXT or add competing SPF records without a migration plan.
    3. Explicitly approve activation only when ready. cmail uses POST /zones/{zone_id}/email/routing/dns, adding/locking routing DNS records, and requires Zone Settings:Edit. Already-enabled routing is reused.

    Check: Fresh domain routing state is enabled and its DNS requirements are satisfied. A successful request or ./cmail status exit code is not enough. Routing authentication does not establish Gmail outbound domain DKIM alignment.

  11. Add and verify the destination inbox

    1. Open Email Routing → Destination Addresses in the zone’s owning account. Destination addresses are account-scoped and reusable. Reuse an existing verified or pending entry for DEST_EMAIL.
    2. If absent, approve adding your exact receiving address and sending a verification email. Open that mailbox’s Inbox/Spam and click Cloudflare’s Verify email address link yourself.
    3. Refresh destination state. If the link is missing/expired, use the dashboard’s resend action deliberately; keep the pending entry instead of making duplicates.

    Check: The exact destination shows verified state/timestamp in a fresh dashboard or authenticated list read. Pending status or merely clicking a link is insufficient.

  12. Create and inspect every forwarding rule

    1. Open Email Routing → intended domain → Routing Rules → Create routing rule. For each ADDRESSES local part, select the domain, choose Send to an email, and select your verified DEST_EMAIL. Save only after reviewing the exact mapping.
    2. Inspect full details for every requested local@DOMAIN: one intended enabled literal “to” matcher, forwarding to exactly your destination. A catch-all is not required.
    3. Do not overwrite unrelated/disabled/conflicting rules silently. Correct only the intended conflict after approving it and inspect fresh state again.

    Check: Every requested alias has the correct enabled rule, no conflicting duplicate, and the intended destination. A truncated status listing or successful create request does not prove this.

  13. Optional: configure Gmail aliases for sending

    Skip this step if you only need to receive mail. It applies only when you want to send from the custom address and DEST_EMAIL is a Gmail/Google account. ./cmail send-as prints the same guidance; source ./cmail setup does not run it. The legacy pinned installation still shows the Gmail guide during setup; ignore that guide for receive-only use (the skill recognizes its post-receiving pause).

    First recheck Google’s January 2027 Send as restriction. If unavailable or prohibited, stop; an alternative mail service is outside this workflow. This is not Google Cloud OAuth app creation or Workspace provisioning.

    1. Open Google Account → Security for DEST_EMAIL and enable 2-Step Verification if allowed. Then open App Passwords, choose a descriptive app name (Mail/cmail if prompted), create an App Password and store it privately. It is displayed only once; never use the ordinary login password.
    2. App Passwords may be unavailable for security-key-only 2-Step Verification, work/school organizational accounts or Advanced Protection. Respect policy; do not disable protection. Changing the Google account password revokes App Passwords; revoke unused/leaked ones.
    3. On desktop Gmail, Settings → See all settings → Accounts and Import (or Accounts) → Send mail as → Add another email address. Enter your name and exact custom alias you own; keep “Treat as an alias” for this same-person alias if shown.
    4. If SMTP is requested, the existing cmail path uses smtp.gmail.com, port 587, TLS, full DEST_EMAIL as username and that account’s App Password. Enter the password directly in Gmail’s dialog, not .env, this page, browser localStorage or chat. Do not select an unsecured connection. This path is subject to Google’s current acceptance/policy, not a guarantee.
    5. Add Account / Send verification, receive the Gmail confirmation through the already-working forwarding rule, and complete the link/code locally. Repeat for every alias you want to send from. Do not share confirmation codes.
    6. Inspect Gmail settings for each confirmed alias. When composing choose the custom From address. Set default From/reply-to deliberately if desired; replies otherwise may go to the original Gmail address.

    Check: Each requested outbound alias is confirmed in Gmail settings, or you chose receive-only and skipped this step. A CLI pause, Enter key, App Password creation or Sent folder entry does not prove delivery. Recipients may see “on behalf of” your Gmail address; this workflow does not guarantee domain DKIM alignment.

  14. Test delivery from an independent mailbox

    1. For every alias, send a unique benign test from a different mailbox (not DEST_EMAIL) to the custom address. Confirm arrival in DEST_EMAIL; check Spam. Same-account forwarding can be suppressed by providers.
    2. Only if you set up sending in step 13: in Gmail compose from that exact custom From address to the independent mailbox. Confirm arrival there (including Spam) and inspect the actual From/reply-to address. A Sent entry alone is not success. Reply back to the alias as an extra check.
    3. If inbound fails, return to active zone, routing DNS, verified destination and exact rule. If outbound fails, return to Google availability, SMTP/TLS, username/App Password and alias confirmation. After repair repeat the affected tests for affected aliases.
    4. Record only sanitized alias/direction/time/result privately, not message bodies, credentials or codes. End-to-end observations do not promise universal delivery, sending limits or compliance. For help use the targeted troubleshooting guide.

    Check: Independent inbound receipt is observed for each requested alias, and outbound receipt too when you set up sending. If sending was requested and only inbound works, record outbound as blocked; do not check the whole setup complete.
